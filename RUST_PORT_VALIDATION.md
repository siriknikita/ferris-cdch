# Rust port validation

**Verdict.** The Rust implementation reproduces the canonical JavaScript CDCH bit for bit on
every tested input: 713 differential cases, 18,003,700 ray samples and 64,832,000 matrix values,
with zero mismatches in sampled coordinates, multiplicities, integer counts, normalized CDFs or
the reduced checkpoint output. The harness detects all 15 deliberately wrong variants of the
algorithm. Derived features agree with NumPy bitwise where the NumPy evaluation order can be
reproduced, and otherwise to ≤ 2.1·10⁻¹⁵ (A) and ≤ 8.1·10⁻¹³ (B) relative difference.

Machine-readable evidence: `reports/differential/differential_results.json` (per case),
`reports/classifier_compatibility/feature_agreement.csv`, `reports/results_summary.json`.

that this tracing harness returns the same matrix as the archived oracle, bit for bit.

## 2. Semantics established from the source

All items were read from `ip-1.js` (`drawRaysAndGenerateHistograms`,
`calculateCumulativeHistogram`), not from the summary documentation.

| Aspect | Canonical behaviour | Rust (`cdch-core`) |
|---|---|---|
| Rays | `for (angle = 0; angle < 360; angle += step)`; 360 rays at step 1 | `Params::angles()`; integer steps 1..=360 (the UI's own validation) |
| Direction | `radians = (angle - 90) * (Math.PI / 180)`; `(Math.cos, Math.sin)`; 0° is up (−y), angles increase clockwise on screen | V8 bit patterns embedded (`directions_v8.rs`), see §3 |
| Radius | `for (r = 0; r < rayCanvas.width; r++)`; **limit is the canvas width**, also for tall images | same; tested on 17×300, 50×200, 64×128 |
| Coordinates | `Math.round(x + r * cos)`, `Math.round(y + r * sin)`, binary64, no FMA | `js::round` (ties toward +∞, `−0` preserved) on separately rounded `x + r*cos` |
| Boundary | `if (px < 0 \|\| px >= width \|\| py < 0 \|\| py >= height) break;` (−0 passes) | identical comparisons on f64 |
| Pixel | oracle `getImageData(x, y)` → `pixels[(y*w + x)*3 + c]` | `RgbImage::rgb(px, py)`, row stride aware |
| Luma | `Math.round(R*0.2125 + G*0.7154 + B*0.0721)`, left to right | `js::luma`; table form `js::luma_fast` proven equal on all 2²⁴ colours |
| Histogram | `rayHistogram[intensity]++`, duplicates from rounding counted with multiplicity | per-ray counts over the plan's sample list, multiplicity preserved |
| Normalization | Number cumulative sum, then `value / cumulative[255]` (one IEEE division per bin) | integer cumulative count, same single division; never a reciprocal multiply |
| Empty ray | `0 / 0 = NaN` in all 256 bins | identical NaN rows; representations that validate (A, B) reject them |
| Output | array of 360 rows × 256 Numbers | row-major `rows × 256` `f64` |
| Centre | archived pipeline sends `[w // 2, h // 2]`; oracle default and UI button use `w / 2` | `Center::archived` (default) and `Center::midpoint`; any finite f64 accepted |

Centres are validated to be finite. The JavaScript would silently produce NaN histograms for a
NaN centre. This is the only input the Rust API rejects that the JavaScript accepts, besides
non-integer angle steps that the UI never produces.

### Rounding

`js::round(x)` computes `f = floor(x)` and returns `f + 1` iff `x − f ≥ 0.5`. For `x ∈ [−1, −0.5)`
the subtraction `x − (−1)` is exact (result in `(0, 0.5]`, finer ulp). For `x ∈ [−0.5, 0)` it may
round, but the true value is then `≥ 0.5`, so the decision is unaffected. For `|x| ≥ 2⁵²`, `x` is
integral. The 19 edge values in `js::tests::math_round_semantics` (including
`0.49999999999999994`, `−0.5`, `±4503599627370495.5`) were checked against `node -p` output.

## 3. The direction table and host libm

For 37 of the 360 integer angles, macOS libm's `cos`/`sin` differ from V8's by one ulp
(`cargo test -p cdch-core --release report_v8_vs_libm -- --nocapture`). The Rust core therefore
embeds the V8 bit patterns (generated by `oracle/direction_table.js` →
`scripts/gen_direction_table.sh`), so results do not depend on the host's libm. The `radians`
argument itself is identical in both.

On ordinary fixtures (integer or half-integer centres, natural images), those one-ulp differences
never changed a rounded coordinate (0 of 705 non-adversarial cases). The table nonetheless matters.
`synth::libm_adversarial_centres` finds centres where `x + cos` lands on a rounding boundary for
one of the two cosines. On those 8 fixtures the libm variant samples different pixels in 12 rays,
and the V8-table implementation still matches the JavaScript exactly.

**Caveat.** The archived matrices were produced with Node v24.22.1 on Linux x86-64. Node 24 could
not be installed here, so the embedded table was generated with Node 22 (V8 12.4). For the
archived protocol the evidence is consistent with identical directions: on the 250 regenerated
PNGs whose pixels match the archive, representation C (sector means of 32 CDF columns), computed
through Node 22 and through Rust, equals the archived Linux/Node 24 values bitwise (192,000 of
192,000 values; RUST_CLASSIFIER_COMPATIBILITY.md). This does not prove that the two V8 versions
agree for every angle and centre. Re-run `node oracle/direction_table.js` under Node 24 and diff
the JSON to close the question.

## 5. Harness sensitivity (mutation testing)

`ferris-diff --mutants` evaluates 15 plausible wrong implementations (`cdch_bench::mutants`) on
every case. Each must be detected by at least one fixture.

| Mutant | Cases detecting it (of 713) |
|---|---:|
| Round as `floor(x + 0.5)` | 6 |
| Round half to even | 685 |
| Round half away from zero | 21 |
| Truncate | 699 |
| Integer luma `(2125R+7154G+721B+5000)/10000` | 16 |
| Luma re-associated `R·r + (G·g + B·b)` | 15 |
| Rec. 601 luma weights | 699 |
| Radius limit `max(w, h)` | 6 |
| Radius limit `min(w, h)` | 9 |
| Normalize by reciprocal multiply | 679 |
| Host-libm directions | 8 |
| 0° pointing right | 694 |
| Mirrored angles | 694 |
| Deduplicate repeated coordinates | 686 |
| Skip the centre pixel | 701 |

Three mutants are invisible on ordinary images and needed targeted fixtures:

- **Re-associated luma.** It changes 3,095,613 floating-point sums but only 42 rounded bins out
  of 2²⁴ colours. A first draft of this mutant only commuted the operands, which is exactly
  equivalent in IEEE arithmetic (0 differences, verified exhaustively) and was replaced.
- **`floor(x + 0.5)` rounding.** It differs only at values such as `0.49999999999999994`.
- **Host-libm directions.** See §3.

The integer-luma mutant shows that the binary64 evaluation of the luma formula is observable on
16 fixtures (it rounds exact decimal ties differently).

## 6. Engine and fused path equivalence

The optimized engine is checked against the literal reference port, independently of Node:

- `crates/cdch-core/tests/engine_vs_reference.rs`: 300 random geometries (1–300 px, all centre
  types, steps 1…360), the archived 128² protocol, strided views, NaN rows and invalid input. It
  checks matrices, checkpoints, coordinates and counts.
- `crates/cdch-features/tests/fused_equivalence.rs`: A, B, C and D from fused extraction vs from
  the full matrix, bitwise, on 39 images × 2 centres.
- `js::tests::luma_fast_matches_luma_exhaustively`: all 2²⁴ colours.
- `rich_shortcut_tests`: the zero-PMF libm shortcut vs the original formulas, bitwise, on 20,000
  random rays including `−0.0` inputs.
- `numpy_compat::tests::slice_and_closure_forms_agree_bitwise`.
- `python/tests/test_bindings.py` (23 tests): batch equals single for 1, 2 and all threads;
  fused == unfused == from-matrix; histograms reconstruct the matrix; strided, Fortran-order and
  non-contiguous inputs; error reporting.

The binding tests found one real defect during development. rust-numpy's `as_slice()` also
accepts Fortran-ordered arrays, which were then read in the wrong order. Zero-copy is now limited
to C-contiguous input. All results in the reports were produced from C-contiguous PIL arrays and
were unaffected.

## 7. Feature arithmetic

A, B and C were re-implemented to follow NumPy 2.3.5's floating-point evaluation order, which
was determined empirically (`numpy_compat.rs`):

- contiguous 1-D sums use NumPy's pairwise summation (8 accumulators, blocks of 128);
- reductions over the angle axis (`x.mean(axis=0)`) accumulate sequentially;
- `x**3`, `x**4` and `v**1.5` call libm `pow`, while `x**2` is `x*x`;
- `log2` is libm;
- `np.linspace(0, 1, 256)` is `i * (1/255)` with an exact final 1.0.

Two operations cannot be matched in general:

1. `pmf @ bins` in B is a BLAS matrix-vector product (OpenBLAS on the archived host, Accelerate
   here), whose summation order is library-specific;
2. the eight harmonics in A come from pocketfft. Rust uses a compensated direct DFT for the
   eight required frequencies.

Agreement on the 400 PNG images (Rust fused vs canonical JS → NumPy, same machine):

| Rep. | Values | Bitwise equal | Max abs diff | Max rel diff | Which features differ |
|---|---:|---:|---:|---:|---|
| A | 22,400 | 20,728 (92.5%) | 2.8·10⁻¹⁷ | 2.1·10⁻¹⁵ | only the 8 FFT harmonics (indices 48–55) |
| B | 39,200 | 36,503 (93.1%) | 6.2·10⁻¹⁵ | 3.0·10⁻¹³ (8.1·10⁻¹³ over all encodings) | A's harmonics, and statistics depending on the BLAS dot (B indices 56–63) |
| C / D | 307,200 | 307,200 (100%) | 0 | 0 | none |

The NumPy reference is itself platform dependent. Recomputing the archived features with the
canonical JS on this Mac gives 93.4% (A) and 93.5% (B) bitwise agreement with the archived Linux
values, at the same 10⁻¹⁵ magnitude. The Rust–NumPy differences are therefore of the same size
as NumPy's own cross-platform variation. The Rust matrix fed into the archived NumPy code
(`rust_matrix`) reproduces the canonical-JS features **bitwise in 100%** of values, which
confirms that every feature difference comes from feature arithmetic, never from the CDCH core.
Downstream effects on scores and labels are quantified in RUST_CLASSIFIER_COMPATIBILITY.md.
